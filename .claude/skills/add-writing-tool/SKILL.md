# 新しいライティングツールを追加する

このアプリは「1 画面 = `views/` の 1 ファイル」。画面側はウィジェットを並べて `prompts` で文字列を組み立て、`ui` に渡すだけで、生成・履歴保存・結果表示・書き直しは `core/ui.py` が全部持っている。だから新ツール追加の実質的な作業は **プロンプト設計と入力欄の設計** であって、配線ではない。配線部分は下のチェックリストを機械的に埋めれば終わる。

## 追加前に決めること

ユーザーの依頼から次を確定させる。曖昧なら勝手に決めず、1〜2 個だけ短く聞く（全部聞くと手が止まって鬱陶しい）。

- **ツール名**（例: 「議事録作成」）— そのまま `TOOL` 定数・メニュー表示名・履歴の分類名になる
- **入力**: 短いお題を打つのか、長文を貼る／ファイルを読ませるのか
- **出力形式**: 箇条書きか、表か、見出し付きか、そのままコピーして使える完成品か
- **カテゴリ**: `app.py` の「書く」「整える」「考える」のどれか（原文がある変換系は「整える」、ゼロから作るなら「書く」、発散させるなら「考える」）
- **アイコン**: 既存と重複しない絵文字 1 つ

## 手順（4 ファイル + 検証）

既存ツールを 1 つテンプレートに選ぶと速い。長文を扱うなら `views/summarize.py`、条件を並べて生成するなら `views/blog.py` が近い。

### 1. `core/prompts.py` に関数を追加

ファイル末尾（`refine()` の手前）に、区切りコメント付きで追加する。返すのは `(system, prompt)` のタプル。

```python
# --------------------------------------------------------------------------
# 議事録作成
# --------------------------------------------------------------------------
def minutes(text: str, style: str, focus: str, extra: str) -> tuple[str, str]:
    system = (
        BASE_RULES
        + """

あなたは会議の書記です。
- 発言の言い直し・雑談は落とし、決まったことと残った宿題を優先する。
- 誰が言ったか不明な発言に話者を推測して割り当てない。
出力形式（この見出し構成を厳守）:
## 決定事項
## ToDo（担当・期限つき）
## 議論の要点
## 未決事項"""
    )
    prompt = _lines(
        [
            ("まとめ方", style),
            ("特に拾いたい観点", focus),
            ("その他の指示", extra),
            ("--- 会議の記録 ---", "\n" + text),
        ]
    )
    return system, "次の会議記録から議事録を作成してください。\n\n" + prompt
```

守ること:

- **`BASE_RULES` を必ず土台にする。** 前置きを書かない・事実を捏造しない、といった共通の禁止事項がここに入っている。上書きせず `+` で足す。
- **出力形式は `system` 側に、可変の条件は `prompt` 側に書く。** ユーザーが選んだ値で変わるものだけ `prompt`。この分担を守っておくと、後から「文体が硬い」といった不満が出たとき `system` 文字列だけ直せば済む。
- **`_lines()` に `(ラベル, 値)` のリストを渡す。** 空の項目を自動で落としてくれるので、任意入力を `if` で分岐して組み立てる必要はない。
- **長い原文は最後に置き、`("--- 原文 ---", "\n" + text)` の形にする。** 条件より先に本文が来るとモデルが条件を読み飛ばしやすい。
- 出力形式を厳密に守らせたいときは、`proofread()` や `headline()` のように見出しや表の列名を具体例で書き切る。抽象的に「構造化して」と言うより効く。

### 2. `views/<name>.py` を作成

ファイル名は英小文字（`minutes.py`）。views は関数で包まず、上から下に実行されるスクリプトとして書く。

```python
import streamlit as st

from core import prompts, ui

TOOL = "議事録作成"

ui.page_header("🗒️", TOOL, "会議のメモや文字起こしから、決定事項と ToDo を抜き出します。")
ui.require_api_key()

text = ui.text_input_with_file(
    "会議の記録",
    key="minutes",
    height=280,
    placeholder="文字起こしや手書きメモをそのまま貼り付けてください。",
)

col1, col2 = st.columns(2)
with col1:
    style = st.selectbox("まとめ方", ["標準（決定事項・ToDo・論点）", "決定事項だけ簡潔に", "時系列で詳しく"])
with col2:
    focus = st.text_input("特に拾いたい観点（任意）", placeholder="例: 予算に関する発言")

extra = st.text_input("その他の指示（任意）", placeholder="例: 社外向けなので固有名詞は伏せる")

if ui.submit_button(TOOL, "✨ 議事録にする"):
    if not text.strip():
        st.error("会議の記録を入力してください。", icon="⚠️")
    else:
        system, prompt = prompts.minutes(text, style, focus, extra)
        ui.generate(TOOL, system, prompt, title=text.strip()[:60])

ui.result_area(TOOL, filename="minutes")
```

### 5. 動作確認

同梱スクリプトで AppTest を回す。`TOOL` 文字列の重複チェックとホーム画面への登録漏れチェックも入っている。

```bash
.venv/bin/python .claude/skills/add-writing-tool/scripts/check_view.py views/minutes.py
```

すべての画面をまとめて見るなら `--all`。`--submit` を付けると生成ボタンまで押して、入力が空のときのバリデーションと `GeminiError` の日本語表示まで確認できる。スクリプトは常にダミーキーで走る（`.env` の本物のキーは読ませない）ので、認証で弾かれるだけで生成は走らず、課金もされない。

問題があれば終了コード 1 と直すべき点の一覧を返す。エラーが出たら直してから完了報告する。「たぶん動きます」で終わらせない。

## 事故りやすい点

**`TOOL` 文字列が識別子を兼ねている。** 生成結果の保存先 `st.session_state["result::<TOOL>"]`、クリアボタンや書き直し欄の `key`、履歴レコードの `tool` 欄、すべてがこの 1 つの文字列から派生する。既存ツールと重複させると、片方で生成した結果がもう片方の画面に出るという分かりにくいバグになる。検証スクリプトが重複を検出するので、必ず通しておく。

**`ui.generate()` は末尾で `st.rerun()` する。** そのため生成した実行では `ui.result_area()` に到達しない。結果は次の実行でセッションから復元されて描画される。この二段構えが前提なので、`generate` → `result_area` の順序を入れ替えたり、`else` の中に `result_area` を入れたりすると結果が表示されなくなる。`result_area` はファイル末尾に、条件分岐の外側で 1 回だけ呼ぶ。

**`st.form` は使わない。** フォーム内の `st.file_uploader` は submit されるまで再実行を起こさず、`ui.text_input_with_file()`（アップロード内容を「直接入力」タブの `text::<key>` に流し込む方式）が動かなくなる。素のウィジェット + `ui.submit_button()` で統一する。

**`text_input_with_file` の `key` も画面ごとに固有にする。** `text::<key>` `upload::<key>` `loaded::<key>` の 3 つの session_state キーを作るので、他の画面と同じ値を渡すと入力内容が混ざる。ファイル名（拡張子なし）をそのまま使うのが安全。

**設定 UI は view に書かない。** モデル・temperature・高速モードはサイドバー（`core/config.py`）で確定し、`config.current()` 経由で読む。view 側に `st.selectbox("モデル", ...)` のようなものを足すと、サイドバーの設定と食い違って混乱する。ツール固有の設定に見えても、生成パラメータ系は触らない。

**API の例外は握らない。** SDK の例外は `core/gemini.py` の `_friendly()` が日本語メッセージに変換して `GeminiError` として投げ、`ui.generate()` が `st.error` で表示する。view に `try/except` を書くと二重にエラーが出るか、握りつぶして無反応になる。view が書くべきエラーは「入力が空」などのバリデーションだけ。

**`filename=` は半角英数にする。** ダウンロードボタンのファイル名に使われ、日本語だと環境によって文字化けする。

**新しい依存は足さない。** DB・認証を持たないローカル単独実行が前提。永続化が必要になっても `data/*.jsonl` 方式（`core/history.py` が手本）を踏襲する。

## 書くもの全部日本語

UI 文言、コード内コメント、プロンプト、`st.error` のメッセージ、docstring —— すべて日本語で書く。変数名・関数名・ファイル名だけが英語。

## チャット型・履歴型など、定型に収まらない画面

上のテンプレートは「入力 → 1 回生成 → 結果表示」型のツール向け。会話を続ける画面や一覧を出す画面はこの型から外れるので、`views/chat.py`（`gemini.stream_chat()` と `st.chat_message` を使い、`ui.generate` は使わない）や `views/history_view.py` を読んでから書く。ただしこの場合も、`app.py` と `views/home.py` への登録は同じように必要。
