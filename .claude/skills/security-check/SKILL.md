# セキュリティ点検とレポート作成

## この点検の考え方

LLM アプリの危険度は、コードだけを見ても決まらない。同じ「認証が無い」でも、本人の Mac だけで動く道具なら仕様であり、社内 LAN に置いてあるなら要注意、インターネットに出ているなら重大になる。だから**最初に配置形態を確定させ、それを掛け算して深刻度を出す**。この順序を守らないと、危険度の判定が当てずっぽうになるか、教科書的な指摘が文脈と無関係に並ぶ。

もうひとつ、LLM アプリに固有の事情がある。守る対象が設定ファイルだけではなく、**利用者が貼り付けた文章そのもの**だという点だ。会話履歴、生成物、アップロードした資料には、社外秘のメールや議事録がそのまま残り、しかも外部の推論 API へ送信されている。従来の Web アプリの点検表には出てこないが、実務ではここが一番効く。

## 手順

### 1. 配置形態と扱うデータを確定させる

以降の判定がすべてここに依存するので、最初に決める。コードや README、`.streamlit/config.toml`、デプロイ設定、CI の有無から読み取れることが多い。読み取れない場合、**推測で進めず利用者に聞く**（ここを間違えると、レポート全体の深刻度がまとめて狂う）。

- **配置形態**: ローカル単独（本人の端末のみ）／ 社内共有（LAN・VPN・社内ネットワーク）／ 一般公開（インターネット）
- **認証の有無**: あるなら、その実装も点検対象に含める
- **扱うデータの機微度**: 個人の下書き程度か、業務の機密や個人情報を含むか
- **LLM プロバイダと契約形態**: 無償枠か有償か。エージェント機能（ツール実行）を持つか

### 2. 機械的に判定できる項目を流す

```bash
python .claude/skills/security-check/scripts/scan.py <対象ディレクトリ>
python .claude/skills/security-check/scripts/scan.py <対象ディレクトリ> --deps   # 依存の既知脆弱性も見る（pip-audit が必要）
```

対象プロジェクトには依存しない。まず構成（フレームワーク・LLMプロバイダ・エージェント機能・アップロードの有無）を判定し、関係する項目だけを点検する。冒頭に出る構成の判定結果は、レポートの「構成」欄にそのまま使える。

見ているのは、秘密情報の露出（ファイル権限・git 管理・直書き・サンプルファイルへの混入。Google / OpenAI / Anthropic / HuggingFace / AWS / Slack / GitHub の各形式に対応）、利用者データが git 管理から漏れていないか、Streamlit の公開設定、危険なコードの書き方（`shell=True`・`eval`・`pickle`・`allow_dangerous_deserialization`・`verify=False`・`unsafe_allow_html`・`st.exception`・session_state の垂れ流し・秘密情報のログ出力）、そして LLM にツール実行権限を与えている痕跡。

**結果を鵜呑みにしない。** 正規表現による判定なので、書き方によっては拾えないし、逆に無害なものを拾うこともある。指摘された箇所は必ず開いて裏を取る。取れなかったものはレポートに載せない。

### 3. 人が判断する観点を見る

機械では判定できないが、実務ではこちらのほうが効くことが多い。

**保存されているデータを実際に開く。** 履歴ファイル、ログ、アップロード先、生成物の保存先。直近の数件がどういう内容かを確かめ、件数・最古の日付・機微な内容の有無を把握する。**中身をレポートに転記しないこと**（レポート自体が新しい漏洩経路になる）。「取引先名を含むメール本文が 12 件」のように、性質と件数で書く。

**LLM プロバイダに何を送っているか。** 入力は外部のサーバーに送られる。無償枠や個人向けプランでは入力がモデルの改善に使われる場合があり、有償・エンタープライズ枠では使われないのが一般的だが、条件はプロバイダと契約によって違う。機密を扱う運用なら、これは設定の不備ではなく**利用形態そのもののリスク**なので、事実として書いて判断を仰ぐ。ログ保持期間とデータの所在地（リージョン）も、規程がある組織では論点になる。

**プロンプトインジェクションを、ツール権限の広さで評価する。** 読み込ませた資料に「これまでの指示を無視して〜」と書かれていれば、モデルはそれに従いうる。深刻度はモデルが**何をできるか**で決まる。
- ツールを持たない（文章を生成するだけ）→ 起きるのは出力の改ざんまで。生成物を検証せず外に出す運用でなければ低い
- ファイル読み書き・シェル・HTTP リクエストを持つ → 情報の持ち出しや破壊につながる。重大に振る
- 検索やデータベース参照を持つ → 参照範囲のデータが引き出されうる

**認証があるなら、その実装を読む。** 自前のパスワード照合（平文比較・固定文字列）、`st.secrets` に置いたパスワード、`streamlit-authenticator` の設定などを確認する。認証が「あることになっている」だけで実質機能していない例は多い。

**コストの上限。** 公開されている LLM アプリに利用制限が無ければ、第三者が API を叩き続けるだけで課金が膨らむ。可用性ではなく金銭の問題として扱う。

**アップロードファイルの扱い。** 受け入れる拡張子、サイズ上限、保存先のパス組み立て（利用者由来の文字列をそのままパスに使っていないか）、解析ライブラリのバージョン。

**前回以降に増えたコード。** 特に外部通信、ファイル書き出し、`subprocess`、新しい SDK。git があれば差分を見る。無ければ更新日時の新しいものから当たる。

### 4. 深刻度を決める

配置形態との掛け算で出す。この表は出発点で、実際の条件（認証の有無、扱うデータの機微度）で上下させてよいが、**上下させたら理由をレポートに書く**。

| 見つかったもの | ローカル単独 | 社内共有 | 一般公開 |
|---|---|---|---|
| 秘密情報が git 管理下・公開リポジトリにある | 🔴 重大 | 🔴 重大 | 🔴 重大 |
| コード内に秘密情報を直書き | 🔴 重大 | 🔴 重大 | 🔴 重大 |
| 任意コード実行につながる書き方 | 🟡 要注意 | 🔴 重大 | 🔴 重大 |
| 認証が無い | 指摘しない（仕様） | 🟡 要注意 | 🔴 重大 |
| 全インターフェースで待ち受け | 🟡 要注意 | 前提条件 | 前提条件 |
| 利用者データが平文で蓄積 | 🔵 情報 | 🟡 要注意 | 🔴 重大 |
| 秘密情報ファイルの権限が緩い | 🟡 要注意 | 🟡 要注意 | 🟡 要注意 |
| プロンプトインジェクション（ツールなし） | 🔵 情報 | 🔵 情報 | 🟡 要注意 |
| プロンプトインジェクション（ツールあり） | 🟡 要注意 | 🔴 重大 | 🔴 重大 |
| 利用量・コストの上限が無い | 🔵 情報 | 🟡 要注意 | 🟡 要注意 |
| 依存ライブラリの既知の脆弱性 | 到達可能性で判断 | 到達可能性で判断 | 🟡 要注意以上 |

**成立条件を書けないものは深刻度を下げる。** 「〜の可能性がある」としか書けないなら、それは要注意ではなく情報。全部を重大にすると優先順位が消え、レポートが読まれなくなる。

### 5. レポートとして出力する

この様式で出す。埋められない欄は「該当なし」と書き、欄ごと消さない（何を見ていないかが伝わらなくなる）。

```markdown
# セキュリティレポート: <アプリ名>

**点検日**: YYYY-MM-DD ／ **対象**: <パス、git があればリビジョン>
**構成**: <フレームワーク> / <LLMプロバイダ> / エージェント機能: <あり・なし>
**想定した配置形態**: <ローカル単独 / 社内共有 / 一般公開>（根拠: <どこから判断したか>）

## 総評
<3行以内。今の状態で使ってよいか。先に直すべきものは何か。>

## 指摘一覧
| ID | 深刻度 | 分類 | 概要 | 対処の目安 |
|----|--------|------|------|-----------|
| C-01 | 🔴 重大 | 秘密情報 | <一行> | 公開前に必須 |
| W-01 | 🟡 要注意 | 公開範囲 | <一行> | 早めに |
| I-01 | 🔵 情報 | 利用者データ | <一行> | 任意 |

## 指摘の詳細

### C-01 <タイトル>
- **該当**: `path/to/file.py:42` または設定項目名
- **何が起きるか**: <攻撃手法の名前ではなく、この利用者に実際に起きること>
- **成立条件**: <これが成り立つために必要な前提。書けないなら深刻度を下げる>
- **確認方法**: <再現手順、または確認できるコマンド>
- **対処**: <そのまま適用できるコマンドか差分>

## 判断が必要な事項
<運用次第で是非が変わるもの。選択肢とそれぞれの結果を併記し、決めるのは利用者に委ねる。>

## 確認済みで問題がなかった項目
<何を見たかを列挙する。ここが無いと点検の網羅性が伝わらない。>

## 点検の範囲と限界
<静的な確認にとどまる旨、見ていない領域（実際の通信内容、インフラ、認証基盤、依存の推移的な中身など）を明記する。>
```

書き方の要点:

- **影響を具体的に書く。** 「XSS の可能性があります」ではなく「同じネットワークにいる人があなたのAPIキーで生成し放題になり、保存済みの履歴も読めます」。読んだ人が判断できる言葉にする。
- **秘密情報そのものを書かない。** 見つけても `sk-p…（48文字）` のように伏せる。
- **問題が無ければ、無いと言い切る。** 何か指摘しないと仕事をしていないように見える、という理由で軽微な項目を膨らませない。「重大・要注意はありません」と書けることには価値がある。
- **対処は、そのまま実行できる形で書く。** 「適切に権限を設定してください」ではなく `chmod 600 .env`。

### 6. 直す

不可逆なもの（**秘密情報の再発行**、履歴やログの削除、git 履歴の書き換え）は、必ず確認を取ってから。取り返しがつかず、「本当に漏れていたか」の判断は利用者にしかできない。

設定ファイルへの追記や `.gitignore` の追加といった軽微な修正は、内容を示したうえで適用してよい。修正後は `scan.py` を再実行して消えたことを確かめ、アプリが壊れていないことも確認する。

**そのアプリの設計方針を壊す「対策」を持ち込まない。** 認証機構、ユーザー管理、外部の秘密情報管理サービスは、セキュリティ的には正しく聞こえるが、ローカル単独実行の道具に入れれば過剰であり、使えないものになる。既存の構成（設定の置き方、データの保存形式、UI 文言の言語）に合わせて直す。

## 過剰な指摘を避ける

| 指摘 | 扱い |
|---|---|
| 認証が無い | 配置形態で決まる。ローカル単独なら指摘しない。**ネットワークに開いている場合のみ**重大 |
| DB を使っていない / SQL 対策が無い | DB が無いなら指摘しない |
| `.env` に平文で秘密情報がある | 標準的な運用。**権限**と**git 管理下に入っていないか**を見る |
| モデル出力を Markdown で表示している | `unsafe_allow_html` が無ければ問題なし |
| 入力文字数やレート制限が無い | ローカル単独なら情報どまり。公開されているなら課金の観点で要注意 |
| 依存に脆弱性がある | CVE の存在だけで重大にしない。その機能を実際に使っているかで判断する |
| `temperature` が高い / モデルが古い | セキュリティの指摘ではない |

## 他のプロジェクトで使う

このスキルは対象プロジェクトに依存しない。別のリポジトリでも使うなら、ディレクトリごと `~/.claude/skills/` にコピーすれば、どのプロジェクトからでも呼び出せる。`scan.py` は対象ディレクトリを引数で受け取るので、置き場所と点検対象は別々でよい。
